
## 24.0 构建连续失败的四轮，逐轮定位（2026-10-25 凌晨）
设备已升 LineageOS 24.0：uname `5.10.269-gki-geff4b40407a1`（= lineage-24.0 分支头
`eff4b40407a1`），Android 17，clang 22.0.2 / based on **r596125**。
官方配置把 namespace 全关了（SYSVIPC/POSIX_MQUEUE/PID_NS/USER_NS 全 n），
所以 Droidspaces 的 MUST HAVE 过不了 —— 必须由我们打开。

**run 40107279212（8de3157）**：5 秒失败。
overlay-config.py 收到的是「相对内核树」的碎片路径，而脚本在仓库根跑 → FileNotFoundError。
修：$FRAGS 统一转绝对路径。

**run 40108493647（1172f75）**：编完 23 分钟、Image 43M，但 ABI 红 1820。
原因：那轮 reference/device-config.txt 还是 23.2 的、基线也是 23.2 的，
而内核树是 24.0 的 —— 三者版本错配。（这轮证明「编译链路本身没问题」。）

**run 40110298580（81190d4）**：1 分 43 秒失败，「组装内核工作区」。
根因是 AOSP clang 归档的两个坑（r596125 在 GitHub 上没有任何镜像）：
  1. 分支名不是 `main`。AOSP 改名两次：master-kernel-build-YYYY →
     main-kernel-build-YYYY → main-kernel-YYYY。r596125 只在 **main-kernel**。
  2. **空归档陷阱**：每个 kernel 分支的树里列出所有 clang 版本目录，只有建分支时
     真正用到的那个有工具链，其余是 .keep 占位符；对占位符下载归档返回 **HTTP 200
     + 约 165 字节的合法空 tar.gz**，解压"成功"但目录为空。
  修：assemble 脚本加 branch/version 映射表 + 归档大小 <100KB 判占位符 + 解压后
  必须 `-x bin/clang`。这两个坑是从 xingguangcuican6666/ABK 的
  scripts/toolchain.sh 里学到的（它有一张 verified-good 表和陷阱说明）。

**run 40111314558（c862188）**：19 分钟失败，`exit code 143`。
143 = SIGTERM，且 **连 `if: always()` 的诊断步骤全被 skipped**（step 失败不会跳过
always，只有 runner 进程被外部终止才会）→ OOM。
对照：同一棵树同一份配置，clang 20 (r547379) 能跑完 23 分钟；clang 22 明显更吃内存。
修：swap 8G → **32G**（按 /mnt 实际空间算 + 断言 Swap 真的起来），
`-j$(nproc)` → **-j3**。→ 下一轮编译成功。

**run 40113421436（028a5bb）**：编译 success、Image 41M，ABI 只差 **23 个符号**。
23 个全在 sched 子系统：runqueues / root_task_group / wake_up_process /
__task_rq_lock / activate_task / deactivate_task / resched_curr / set_task_cpu /
sched_setattr / sched_setscheduler(_nocheck) / sched_set_fifo / sched_set_normal /
sched_show_task / set_user_nice / update_rq_clock / uclamp_eff_value /
task_may_not_preempt / migrate_swap / cpupri_find_fitness /
pick_highest_pushable_task / check_preempt_curr / set_cpus_allowed_ptr

**元凶 = CONFIG_CFS_BANDWIDTH**（唯一 sched 相关改动）。
机理：它给 kernel/sched/sched.h 的 `struct cfs_rq` 加 throttled 字段、给
`struct task_group` 加 `struct cfs_bandwidth cfs_bandwidth;`；而 **genksyms 会递归
解析嵌套类型** —— task_struct 里嵌 `struct sched_entity se`，se 里又有
`struct cfs_rq *cfs_rq` → task_struct 指纹跟着变 → 所有签名带 task_struct*/rq*/
task_group* 的导出符号全变。**这是「嵌套递归」型 ABI 破坏，KABI 保留槽救不了。**
（KernelSU_Action 的 config.env 早就把它标成 =n，注释原文：
 "struct changes, never ABI-verified on this device" —— 现在有实锤了。）

代价：Droidspaces 的 `--cpus` 用不了。拿回只能连 vendor 模块一起重编重刷。

## 24.0 最终配置（与设备 /proc/config.gz 只差 8 项，全是新增）
  CONFIG_PID_NS / CONFIG_USER_NS
  CONFIG_POSIX_MQUEUE / CONFIG_POSIX_MQUEUE_SYSCTL / CONFIG_IPC_NS
  CONFIG_MACVLAN / CONFIG_IP6_NF_NAT / CONFIG_IP6_NF_TARGET_MASQUERADE
不动的：SYSVIPC（设备 n，开了 task_struct 多两成员）、KSU（用户不要）、
CGROUP_DEVICE/PIDS（css_set 定长数组）、CFS_BANDWIDTH（嵌套递归，实测 23 符号）、
NF_TABLES（struct net）。

## 24.0 的 ABI 基线
从设备 390 个 .ko 重建，**4188 符号**；与 23.2 那版对比只有 1 个符号 CRC 变了
（ipa3_ctx）⇒ 老的「哪些配置安全」结论依然适用。
