## ★★★★ 卡在米标的真凶：ABI 不兼容（CONFIG_SYSVIPC / CONFIG_NF_TABLES 改了结构体布局）
### 现场
Run#6 全绿（版本串 + clang 21 都对），用 magiskboot 打成 boot.img 写 boot_b，
回读 md5 一致 → 重启**永远停在米标**；fastboot 刷回备份立即恢复。
排查：`/sys/fs/pstore/` 空、dropbox 无 `SYSTEM_LAST_KMSG`、无 tombstones
⇒ **是 hang 不是 panic**，所以根本没日志可看。

### 根因（源码级证据，已用头文件逐行确认）
GKI 内核与 ROM 的 395 个 `/vendor/lib/modules/*.ko` 是**分离编译**的；
模块把"所需符号的 CRC"写在 `__versions` 段，内核加载时比对，不一致就拒载。
CRC 由 `genksyms` 从**类型定义**算出 → 改了结构体布局 = 相关导出符号 CRC 全变。
- `CONFIG_NF_TABLES=y` → `include/net/net_namespace.h:145`
  `#if defined(CONFIG_NF_TABLES) ... struct netns_nftables nft;`
  → `struct net` 多成员，所有含 `struct net *` 的导出符号 CRC 全变
- `CONFIG_SYSVIPC=y` → `include/linux/sched.h:973`
  `#ifdef CONFIG_SYSVIPC ... struct sysv_sem sysvsem; struct sysv_shm sysvshm;`
  → `struct task_struct` 多两个成员，影响面更大

症状为什么正好是"卡米标"：米标是 bootloader 画的，内核接手屏幕要靠
vendor 模块里的显示驱动（`msm_drm.ko`）；模块集体拒载 → 显示驱动没加载
→ 屏幕永远停在米标。

### 修复（commit 6a71268）
- fragment 移除 `NF_TABLES` / `NF_TABLES_BRIDGE` / `BRIDGE_NETFILTER`；
  `IPC_NS` 的前置项 `SYSVIPC` → **`POSIX_MQUEUE`**
- `verify-built-config.sh` 新增 `FORBIDDEN_Y`（NF_TABLES/SYSVIPC 必须非 y）
- workflow 新增「兜底 sed 删除危险项」+「**ABI 预检**」步骤
- 新增 `scripts/check-abi-crc.py`（解析 ELF `__versions` / `Module.symvers`）
- 新增 `abi-baseline/abi-crcs.txt`：从真机 10 个模块抽出 **1613 个符号的 CRC 基线**
- Docker 侧适配：内核**没有** NF_TABLES，必须用 **iptables-legacy**；
  好消息是 `NETFILTER_XTABLES`/`IP_NF_IPTABLES`/`IP_NF_NAT`/
  `IP_NF_TARGET_MASQUERADE`/`NF_CONNTRACK` 全族 **=y 内建**，够用。

### 自测
- 配置校验：用设备真实 /proc/config.gz 当 base 模拟合并 → `PASS=31 FAIL=0`
- ABI 比对器：CRC 一致 → 退出 0；人为改 3 个 → 精确报出并退出 1

## 交付物形态（用户问过两次，记牢）
**CI 产物只有裸内核 `Image`，没有 `boot.img`。** 这是刻意设计：只做 `make Image`。

## bisect 终局（G 绿 / H 红）—— 725 与 295 的真正元凶（本次收口）
- **G（FRAGMENT=userns，b5aa8ee：D2 + 只开 USER_NS）→ 绿**：`CONFIG_USER_NS` 对 ABI 零影响。
  注意 5.10 这棵树里 `struct user_struct.locked_vm` 的条件是
  `#if defined(CONFIG_PERF_EVENTS) || defined(CONFIG_BPF_SYSCALL) || defined(CONFIG_NET) || defined(CONFIG_IO_URING)`

- **H（FRAGMENT=ipc，9e3934f：POSIX_MQUEUE + IPC_NS + POSIX_MQUEUE_SYSCTL）→ 红 725**，
  且**失配集合与 CRC 值与 F2（整组 ns）逐个完全相同** ⇒ 整个 725 来自 POSIX_MQUEUE。
- **725 = `struct user_struct` 多一个成员**：`include/linux/sched/user.h:24`
  `#ifdef CONFIG_POSIX_MQUEUE unsigned long mq_bytes;` → 经 `cred.user` 被
  task/file/socket 广泛引用。已验证 `ipc_namespace.h`（mq_* 成员无条件）、
  `nsproxy.h`（无 guard）、`ipc.h/msg.h`（无 guard）都不背锅。
- **295 = `struct css_set` 定长数组**：`CGROUP_SUBSYS_COUNT` 设备上 7
  （cpuset/cpu_cpuacct/io/memory/freezer/net_prio）→ 开 DEVICE/PIDS 变 9。
  KABI 保留槽救不了数组长度 ⇒ **CGROUP_DEVICE/CGROUP_PIDS 只能放弃**。
- 295 ⊂ 725，且两者在 295 上的 CRC 值互不相同（两种机制独立叠加），这一点是判据。
- **修法（已落地，commit d1abe3b）**：`scripts/patch-abi-safe.sh` 把 mq_bytes 挪进
  KABI 保留槽 —— `ANDROID_KABI_RESERVE(2)` → `ANDROID_KABI_USE(2, unsigned long mq_bytes)`。
  `android_kabi.h` 里 `#ifdef __GENKSYMS__ #define _ANDROID_KABI_REPLACE(_o,_n) _o`，
  所以 genksyms 看到的文本仍是 `u64 android_kabi_reserved2`（与 ROM 逐字相同）→ CRC 不变；
  编译器侧是 8 字节 union（unsigned long 与 u64 同尺寸同对齐）→ 布局也不变。
  这不是糊弄检查，布局真的没变，正是 KABI 保留槽的设计用途。
  IPC_NS 的依赖只能走 POSIX_MQUEUE（SYSVIPC 会给 task_struct 加 sysvsem/sysvshm，更致命）。
- **新增 FRAGMENT=docker 交付模式** = 整份碎片 − {CGROUP_DEVICE, CGROUP_PIDS}

  preconfig/verify 的必需项清单按模式自适应；docker 与 all 一样走严格校验）。
- **重要方法论**：判断"哪个配置伤 ABI"不必读源码猜 —— 直接跑 CI（push 即编），

  再拿候选配置名去内核头文件里 grep `#ifdef CONFIG_X` 是否落在 struct 定义内佐证。
- **Docker 的代价（必须如实告知用户）**：拿不到 devices / pids 控制器，

## ★★ Docker 在 chroot 里跑通了（2026-10-01 晚，真机实测 + 重启后复验）
### 现场结论
- 内核侧全绿：`/proc/self/ns/` 出现 `pid/ipc/user`；`/proc/cgroups` 仍是那 7 行
  （devices/pids 拿不到，预期内）；`ls /sys/module | wc -l` = 512（含 `msm_drm` 等），
  即 ROM 的 vendor 模块一个没少 → ABI 兼容在真机上闭环。
- Docker：`Server Version 28.2.2 / Storage Driver fuse-overlayfs / Cgroup Version 2`，
  `docker run` 实测回显 `CONTAINER_OK`，容器内 `pid=1`、独立 hostname、
  `ns: cgroup ipc mnt net pid pid_for_children time time_for_children user uts`。
- 完整重启 chroot 后仍自动生效（补丁写进 app 脚本）✓

### 三处修复（缺一不可，全部实测）
1. **`/sys/fs/cgroup` 必须是真 cgroup2**（app 原来挂的是空 tmpfs）
   - Docker 看到非 cgroup2 → 走 cgroup v1 路径 → 启动硬性要求 devices 挂载：
     `failed to start daemon: Devices cgroup isn't mounted`
   - 而本内核**不能**开 `CONFIG_CGROUP_DEVICE`（改 `struct css_set` 定长数组 → 295 符号 CRC 变）
   - cgroup v2 的设备控制走 BPF，`include/linux/bpf_types.h` 里
     `BPF_PROG_TYPE_CGROUP_DEVICE` 只受 `CONFIG_CGROUP_BPF` 约束（我们 =y）→ 不影响设备隔离能力
2. **挂载树 rprivate**（`busybox mount --make-rprivate /`，必须在 chroot 外对真实根做）
   - `fs/namespace.c` 的 `pivot_root`：`IS_MNT_SHARED(root_parent)` → **EINVAL**；
     Android 默认整棵树 shared ⇒ runc 的 pivot_root 恒失败 ⇒ 容器创建报
     `error jailing process inside rootfs: pivot_root .: invalid argument`
   - app 脚本里本来就有这句（注释原文 "prevents peer group conflicts that cause pivot_root
     to fail"），但只在 sparse-image 布局分支里，**目录布局走不到** → 这是本次最大的坑
   - 从 chroot 内部改不到真实根（`/proc/1/root` 解析到 chroot 根），必须用
     `busybox nsenter -t <holder.pid> -m ...` 进 holder 的 ns 执行（app 的 `run_in_ns` 就是干这个的）
   - 另：`mount --make-rprivate` 是 **busybox 语法**，Android 的 **toybox mount 不认**（会报
     `bad /etc/fstab`）—— 所以必须先找到 busybox（app 自带 `/data/local/ubuntu-chroot/bin/busybox` ✓）
3. **rootfs 递归自 bind**（`mount -o rbind $ROOT $ROOT`）
   - 让 chroot 里的 `/` 成为挂载点；否则 dockerd 报
     `Error while setting daemon root propagation ... Can't find mount point of /var/lib/docker`，
     随后 `docker import/run` 报 `remount /, flags: 0x84000: invalid argument`
   - ★ 必须用 `-o rbind`：普通 `--bind` 不带上子挂载，会把已挂好的 `/proc /sys /dev` 全部遮住
     （实测踩过一次，dockerd 报 `open /proc/cpuinfo: No such file or directory`）

### 附带两项
- **存储驱动**：本机内核**拒绝对 f2fs 用 overlayfs** —— `dmesg` 原文
  `overlayfs: filesystem on '...' not supported` / `upper fs does not support xattr`，
  机制是 f2fs 带 **casefold** 特性 → dentry 带 d_hash/d_compare → `ovl_dentry_weird()` 拒绝。
  ⇒ 用 `fuse-overlayfs`（apt 可装，`/dev/fuse` 在、`CONFIG_FUSE_FS=y`）。
  实测 vfs 也能 import，但容器 rootfs 不是挂载点，pivot_root 仍会失败。
- **iptables**：内核按 ABI 要求 `NF_TABLES=n`，chroot 里默认 nft 后端会报
  `Could not fetch rule set generation id: Invalid argument`。daemon.json 里
  `{"iptables": false, "bridge": true→none, "ip6tables": false}` 即可（他们本来就是 bridge=none）。
